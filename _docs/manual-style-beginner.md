# マニュアル執筆ルール — 非技術者・初心者向け

対象読者は **パソコン操作に不慣れな現場・事務スタッフ**。専門用語・英語・
システム内部の話を前提にしない。「画面に見えているもの」だけで話を進める。

## 絶対ルール

1. **英語の状態名を書かない。** `DRAFT` `ISSUED` `PRICE_DIFF` などは出さず、
   画面に出る日本語（下書き / 発行済 / 価格差異）だけを使う。
2. **システム内部の説明をしない。** 「サーバー側で再解決」「自動で採番」等は
   ユーザーの行動に関係する場合のみ、結果だけを書く
   （例: ×「保存時にサーバーで再解決されます」→ ○「保存すると、そのときの
   最新の価格表で単価が入り直します」）。
3. **1 手順 = 1 動作。** 「〜を押します」「〜を選びます」。複文にしない。
4. **画面の文言は「」で囲んで実物どおり**（ボタン名・項目名・タブ名）。
5. **専門語は初出でその場で言い換える。**
   例: 「注文種別（本番・テスト・サンプルなどの区分）」
6. **敬体（です・ます）。** 命令形は使わない。脅かさない。
7. **数式・条件式を書かない。** 「基準単価 × 倍率」のような式ではなく
   「数量が多いほど単価が下がる設定になっています」と説明する。

## ページの型（すべてのアプリページ共通）

```
---
title: "<アプリ名> — 操作マニュアル"
description: "<1 文。何ができるアプリかを平易に>"
screenshots: [id, ...]
---

<1〜2 文。このアプリで何ができるかを、日常の言葉で>

## このアプリでできること

- 箇条書き 3〜5 個。「〜できます」で終える
- 「いつ使うか」を 1 つ入れる（例: お客様に金額を提示するとき）

## 用語（このページで出てくる言葉）

- **用語** … やさしい説明（1 行）
※ そのページで初めて出る業務用語だけ。3〜6 個。無ければ節ごと省略可。

## はじめる前に

- 先に必要なもの・登録しておくものを箇条書き（例: 先に価格表が必要です）
- リンクで該当マニュアルへ

## 画面の見かた

![一覧画面](...)
- 番号や色つきバッジが何を意味するかを箇条書きで

## <操作 1（例: 見積書をつくる）>

1. 手順（1 動作 1 行）
2. …

![該当画面](...)

> 💡 ヒント / ⚠️ 注意 は Callout（`> ` 引用）で。1 ページ 3 個まで。

## <操作 2 …>

## よくある質問・困ったとき

**Q. <実際に起きること>**
A. <対処。原因の説明は 1 文まで>

3〜6 個。エラーメッセージは画面の文言そのままを「」で引用する。
```

## スクリーンショット

- **1 ページ 4〜7 枚**。「一覧」「新規フォーム」「詳細」＋操作の要所。
- 手順の**直後**に置く。alt は画面の内容（「見積書の新規作成フォーム」）。
- ボタンの位置を文章で補う（「画面右上の『新規作成』」）。
- id は `<app>-<画面>-NN`。撮影規約は `tools/docs-screenshots/README.md`。

## 3 ロケール

ja を確定 → en / zh を同内容で。en は平易な英語（専門用語を避ける）、
zh は簡体字。画像は 3 ロケールとも同じ ja 画面のものを共用する。

## 用語の統一

`_specs/design.md` §17 の用語集に従う（「注文書」ではなく「注文請書」等）。
言い換えは初出の補足のみで、見出し・本文の主用語は必ず正式名称を使う。

## プロセス編の例外（content/manual/process/**）

プロセス編（標準フロー + 分野別 5 ページ）は業務文書としての読みやすさを
優先し、以下だけ本規約から外れる。**それ以外の絶対ルール（英語状態名禁止・
内部実装禁止・1 手順 1 動作・「」で画面文言・数式禁止）はそのまま適用する。**

- **文体は常体（である体）**。絶対ルール 6 の「です・ます」を上書きする。
  ただし同ルールの残り — 命令形を使わない・脅かさない — は維持する
  （「〜してください」も「〜せよ」も使わない。「〜する。」「〜する必要がある。」）。
  表のセルは体言止め可。
  - 例: 「確定にします」→「「確定」を選ぶ。」/「自動で付きます」→
    「自動で付与される。」/「作ってください」→「登録しておく必要がある。」
- **ページの型**が違う（アプリページの型は使わない）:
  - 標準フロー: リード → 全体の流れ（SVG 図） → 登場人物 → 段階 1..N
    （`### 操作（だれが・なにを）` + `### システムが自動でおこなうこと`） → 関連ページ。
    段階見出しには明示 id `[#stage-N]` を付ける（分野ページがリンクする）。
  - 分野ページ: リード → 全体の流れ（SVG 図） → 段階ごとの担当とアプリ →
    それぞれの段階でおきること（分岐・例外・判断基準のみ。基本手順は
    標準フロー §N へリンク） → 書類の状態（**正はこちら** — キャンセル・
    差し戻し系も含める） → 止まりやすいところ → 関連ページ。
- **スクリーンショットは赤枠強調付きの `flow-*` を段階ごとに 1 枚**。
  枚数上限（4〜7 枚）は適用しない。id 規約は `flow-<app>-<画面>-NN`
  （撮影は tools/docs-screenshots の `highlight` 指定）。
- **フロー図**は kai-swimlane DSL から生成した SVG
  （`content/manual/assets/diagrams/`、ソースとビルドは `tools/swimlane/`）。
  図中の用語も §17 に従い、システム内部（ライブラリ名・番号フォーマット等）は
  書かない。
- **ロケールは ja のみ**。en/zh ファイルは置かず、既定言語フォールバックで
  ja の内容が表示される（meta.en/zh.json にはページを列挙したままにする）。
- Callout（💡/⚠️ 3 個まで）は通常どおり適用する。
