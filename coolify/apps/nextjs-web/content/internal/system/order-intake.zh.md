客户发送到 **order-intake@ckk-tool.co.jp** 的订单书，无需人工介入即可导入为注文请书 —— 本页说明该机制的运维。面向使用者的操作请参见「[注文書取込（SY0C）](/manual/zh/operations/system/order-intake/user)」。

> 该机制目前**仅在验证环境（dev）**运行。生产环境（main）尚无导入文件夹（见下方「推广到生产环境时」）。

## 整体流程

```
客户 ──邮件──> order-intake@ckk-tool.co.jp （樱花邮件服务器）
                    │  intake-gateway 每 120 秒通过 IMAP 巡回
                    ↓
              导入文件夹（INTAKE_DIR）
                    │  nextjs-web 的轮询器每 60 秒扫描
                    ↓
     采番 ORD- → AI 读取（po-extract）→ 匹配交易方・产品 → 草稿
```

**文件落到导入文件夹之后，与人工直接放入共享文件夹走的是完全相同的路径。** 邮件特有的处理，到「挑出附件并放入文件夹」为止就结束了。

## 相关组件

| 名称 | 是什么 |
|---|---|
| `order-intake@ckk-tool.co.jp` | 客户发送的目标地址。**仅供自动导入，无人查看** |
| `intake-gateway-dev` | 巡回邮箱并将附件写入文件夹的容器（Coolify 管理・仅限内部） |
| 导入文件夹 | `intake-gateway` 与 `nextjs-web` 共享的服务器文件夹 |
| `admintools` | 创建・删除邮件地址。通过自动操作樱花的控制面板实现 |

## 哪些附件会被导入

**会导入** … 扩展名为 **PDF / PNG / JPG / WEBP** 的附件（单个上限 20MB）。传真常见的 TIFF 会先自动转换为 PDF 再导入。

**不会导入**

- 正文中嵌入的图片（例如**签名中的公司标志**）。若将其导入，则每封邮件都会把标志采番为一件注文请书，因此刻意排除。
- `.p7s`（电子签名）・`.ics`（日程）・`.txt`・`.html` 等上述以外的格式。
- 发件人不在允许列表（`INTAKE_MAIL_ALLOW_FROM`）中的邮件。**未设置时全部接收。**

若一封邮件附有 3 份订单书，则会生成 **3 件注文请书**（1 份订单书 = 1 件）。

## 导入后邮件会怎样

| 结果 | 邮件的处理 |
|---|---|
| 全部附件均已导入 | 标记为**已读**，移动至「**Processed**」文件夹 |
| 没有可导入的附件（仅正文・仅签名） | 仅标记为**已读**，保留在收件箱（以便人工查找） |
| 有任何一项失败 | 标记为**已读**，移动至「**Failed**」文件夹。**不会自动重试** |
| 连接・认证失败 | 不做任何处理（保持未读）。下次巡回时重试 |

> **不自动重试失败邮件是刻意的设计。** 对半途成功的邮件再处理一次，必然导致同一份订单书被重复登记（无法按单个附件判断重复）。失败时，请联系发件人重新发送，或保存附件后从注文请书的「优先导入」上传。

## 确认方法

**是否已导入** … 会以 `mail_发件人_文件名` 的形式出现在 SY0C「注文書取込」的「等待导入」中。约 60 秒后采番为 `ORD-…`，并出现在注文请书列表中。

**邮箱侧** … 可用普通邮件客户端打开 `order-intake@ckk-tool.co.jp`（IMAP：`ckk-tool.sakura.ne.jp` / 993 / SSL）。已处理的在「Processed」，失败的在「Failed」。

**是否在运行** … 在服务器上执行 `docker logs intake-gateway-dev`。

| 日志 | 含义 |
|---|---|
| `メール取込を開始します: …` | 正常启动 |
| `未読 N 通を処理します` → `取込フォルダへ配置: …` | 正在导入 |
| `受理できる添付なし` | 无附件，或仅有不支持的格式 |
| `メール取込は無効です（… が未設定です）` | 配置不足（会显示原因）。不会崩溃，进入等待 |
| `取込フォルダが使えません` | 文件夹不可见或不可写。**此状态下不会开始巡回**（以免遗漏订单书） |

## 遇到问题时

**发了邮件却没有被导入**

1. 在邮箱中确认该邮件是否为**已读**。已读即表示已尝试处理。位于「Failed」说明失败；仍在收件箱说明没有可导入的附件。
2. 若仍为未读，说明网关未运行，或邮件未送达。请查看日志。
3. 确认附件格式（PDF・PNG・JPG・WEBP 以外不会导入）。

**出现在「等待导入」却始终「未采番」** … 这是文件夹侧而非邮件侧的问题。请按 SY0C 的「立即扫描」；若仍无变化，请查看 `nextjs-web` 的日志。

**收件箱塞满** … 可能是移动至「Processed」的设置未生效。请确认日志中是否出现 `メールを … へ移せませんでした（既読にはしてあります）`。

## 新建邮箱时

邮件地址的创建由 **admintools** 负责（会自动操作樱花的控制面板）。

1. 在 admintools 的「邮件」画面添加账号。**用户名（username）** 与邮件地址可以不同（系统用窗口的惯例是以 `other-sys.` 开头）。
2. **执行「同步」。** 此时才会在樱花侧真正创建实体。
3. 创建的是**邮件用户**，以及必要时的**别名**两者。当用户名与邮件地址 `@` 左侧不同时，**作为 IMAP 登录名的是邮件地址一方**（`order-intake@ckk-tool.co.jp` 即为此形式）。
4. 将该地址填入 `intake-gateway` 的设置（`INTAKE_MAIL_USER` / `INTAKE_MAIL_PASSWORD`）并重新部署。

> **请勿使用同步中「删除列表中不存在的项」。** 未登记在管理表中的樱花侧邮箱会被删除。执行前务必用「确认差异」查看将被创建・删除的内容。

> **请勿让验证环境与生产环境使用同一个邮箱。** 两个网关会争抢同一封邮件，最终只会在其中一侧被导入。

## 推广到生产环境时

生产环境（main）尚无导入文件夹。推广需要在服务器侧完成以下工作：

1. 创建生产用的导入文件夹（使 `nextjs-web` 与 `intake-gateway` 双方均可写入）
2. 将**同一个文件夹**分配给 `nextjs-web-main` 与 `intake-gateway-main` 两者
3. 准备**生产专用的邮箱**并配置到 `intake-gateway-main`（不与验证环境共用）
4. 在应用管理（SY05）中公开「注文書取込」

详细步骤见 `coolify/apps/intake-gateway/README.md`。

## 不会被记录的内容（已知限制）

**发件人・主题・邮件正文不会记录在注文请书上。** 线索只有以下两项：

1. 文件名中保留的 `mail_发件人_` 部分（保留在 SY0C 列表以及采番后的文件名中）
2. `intake-gateway` 的日志

无法从注文请书的详情画面追溯，也无法检索「来自该交易方的邮件」。这是为了将导入机制与业务数据解耦而作出的取舍。需要确认主题或正文时，请直接打开邮箱。
